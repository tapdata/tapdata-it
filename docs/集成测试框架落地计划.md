## 一、产品组件全景与功能

TapData 是多模块数据集成/实时 CDC 平台，产品运行时组件及功能如下（依据 tapdata-wiki A-20260813-仓库拓扑 与代码盘点）。本表是下文各层"功能模块"划分的来源：

| 组件 | 代码位置 | 核心功能 | 集成测试关注点 |
|---|---|---|---|
| **执行引擎 iengine** | `tapdata/iengine`（iengine-app / iengine-common / iengine-oss / modules / validator） | 任务执行：DAG 编译、任务调度（`TapdataTaskScheduler`）、全量读取（三条路径）、增量读取（offset/断点）、目标端写入（写入策略/exactly-once）、DDL 同步、ShareCdc 共享挖掘、分区分片并发保序、指标上报 | 任务生命周期、数据一致性、断点续跑、事件不丢不重 |
| **管理端 TM** | `tapdata/manager`（tm / tm-api / tm-common / tm-oss；企业版 tm-enterprise） | 控制面：112 个 REST Controller——数据源与连接管理（ds）、连接器/插件版本管理（PdkController/PdkVersionController）、任务与调度（scheduleTasks/taskhistory）、数据校验（inspect）、告警（alarm/alarmrule）、类型映射（typemappings）、外存（externalStorage）、共享 CDC 管理、WebSocket 通信、监控指标（metrics） | API 契约、状态机流转、跨服务联动 |
| **API Server** | 开放 API 服务。**Node.js 版（`tapdata-enterprise/apiserver`）已停止更新，以后由 apiserver-java 替换**：Java 主线为 `tapdata-enterprise/apiserver-java`（企业版替换实现，ADR-0026 跨仓切换进行中）+ 顶层 `apiserver`（`io.tapdata:api-server`，`server_api_definition.json` 定义开放 API 契约）；Agent 经 `conf.apiServerJar` 切换（存在 exec jar→启动 Java 单 JVM，否则回退 Node） | 对外开放 REST API，供第三方系统管理任务/数据源 | 开放 API 契约、鉴权（集成测试聚焦 apiserver-java） |
| **PDK 插件层** | `tapdata-common-lib/plugin-kit`（tapdata-pdk-api / tapdata-pdk-runner） | 连接器接口契约（`TapConnector`/`ConnectorFunctions`）与运行时（`TapConnectorManager` 加载/卸载连接器 jar） | 契约稳定性、插件热加载 |
| **连接器** | `tapdata-connectors/connectors`（80+ 开源）、`tapdata-connectors-enterprise/connectors`（DB2/达梦/GBase 等） | 各数据源读写/CDC/建表等能力实现 | PDK 能力函数行为（L1 主战场） |
| **Agent** | `tapdata-enterprise/tapdata-agent`（Node.js） | 进程编排：拉起/守护 apiserver、引擎等子进程 | 进程编排、崩溃恢复（L3 覆盖） |
| **License 客户端** | `tapdata-license/tapdata-license-client` | License 校验与能力开关 | 校验行为（随 L2 抽测） |
| **Hazelcast（fork）** | `tapdata/Hazelcast`（分支 release-v5.5.0） | 引擎分布式底座：集群协调、分布式数据结构 | HA 行为（L3 覆盖） |
| **前端 tapdata-web** | `tapdata-web`（Vue，pnpm workspace） | 用户界面 | 不单独测试，经由 L3 黑盒覆盖 |

**组件间协作链路**（决定 L2 测试域）：前端/WebSocket → TM（任务编排）→ 引擎（执行）→ PDK → Connector → 数据库；TM 经 `scheduleTasks` 下发任务、引擎回报状态与指标（taskhistory/metrics）；PdkController 管理连接器 jar 的上传与热加载。

## 三、L1：单 Module 集成测试

执行环境：组织级自托管 GitHub Actions runner（`docker/docker-compose.yaml` 编排，label `tapdata-it`，4 副本，privileged + docker.sock 挂载）；测试数据库由 Testcontainers/ConnectorIT 在用例中动态拉起、用完销毁。命名 `*IT.java`，`mvn verify` 执行（Failsafe）。按组件分为 4 个功能模块组：Connector / 引擎 / 管理端 / API Server。

### 3.1 Connector 集成测试（`tapdata-connector-it`，框架 ✅ 已就绪）

[ConnectorIT.java](../tapdata-connector-it/src/main/java/io/tapdata/it/ConnectorIT.java)（2624 行）提供 **74 个通用 `should_*` 用例**，任何 Connector 只需继承并实现 `createContext()` 即可全量运行。三条可靠性原则：旁路验证（用对端数据源验证写入事实，禁止用 read 验证 write）、动作唯一（一个用例只测一个 function）、声明式能力（`requiredCapabilities()` 声明必实现 + 框架级覆盖校验用例）。

**连接器接入状态**（继承 ConnectorIT 即全量运行 74 用例）：

- ✅ **MySQLConnectorIT**（`mysql-connector/src/it`）——接入示例
- ✅ **MongoDBConnectorIT**（`mongodb-connector/src/it`）——接入示例
- ✅ **DB2iConnectorIT**（`db2i-connector/src/it`，企业版 `-P enterprise`）——已验证企业版构建链路
- ⬜ **PostgreSQL / Oracle / Kafka**——首批待接入（标准 1~2 人天/个，复杂 CDC 3~5 人天）

**74 个用例按 12 个功能域分组**（每组标"接入适配预估"，即新连接器方言适配成本；用例本身框架内置）：

- ✅ **① 连接与元数据发现（8）**（0.5 天/连接器）— 验证凭据校验、表发现、TapType 类型映射、连接诊断项符合契约
  - `should_test_connection`：正确/错误凭据调 connectionTest，断言 TestItem 项与错误信息
  - `should_connection_check`：连接诊断项符合契约
  - `should_discover_schema_of_created_table`：随机建表后 discoverSchema，对照 TestTableSpec 断言字段类型
  - `should_find_table_after_create`：建表后可被发现
  - `should_table_not_found_after_drop`：删表后不再被发现
  - `should_get_table_info`：表信息获取
  - `should_check_table_name`：表名合法性校验
  - `should_get_charsets`：字符集枚举
- ✅ **② 建表与表级 DDL（7）**（0.5 天/连接器）— 验证目标端建表/清表/删表/字符集/TTL/时区结果正确且幂等（旁路直连对端核对表结构）
  - `should_create_table_v2`：按 TapType 建表，旁路核对结构
  - `should_create_table_v2_when_exists`：已存在表重复建表的幂等分支
  - `should_clear_table`：清表
  - `should_drop_table`：删表
  - `should_alter_table_charset`：改字符集
  - `should_alter_table_ttl`：改 TTL
  - `should_alter_database_timezone`：改库时区
- ✅ **③ 写读数据一致性（5）**（1 天/连接器）— 生成类型受控随机数据写入→旁路读回逐行比对（RecordAssert）
  - `should_write_insert_records`：插入写入一致性
  - `should_write_update_records`：更新写入一致性
  - `should_write_delete_records`：删除写入一致性
  - `should_batch_read_data_consistent`：batchRead 回读与源端逐行一致
  - `should_batch_count_match`：batchRead 条数与源端匹配
- ✅ **④ 条件查询与过滤（3）**（0.5 天/连接器）— 预置已知数据集，构造 filter 调用并断言命中行
  - `should_query_by_filter`：TapFilter 普通过滤
  - `should_query_by_advance_filter`：TapAdvanceFilter 高级过滤（聚合/排序/分页）
  - `should_query_hash_by_advance_filter`：hash 分片过滤
- ✅ **⑤ 增量读取 CDC（4）**（2 天/连接器，复杂度高）— 容器预置 Binlog=ROW/WAL/Oplog，写入增量后收集事件断言类型与值
  - `should_stream_read_incremental`：Insert/Update/Delete 增量事件
  - `should_stream_read_one_by_one`：单条消费
  - `should_stream_read_multi_connection`：多连接并发消费
  - `should_timestamp_to_stream_offset`：时间戳转 stream offset
- ✅ **⑥ 事务与写入控制（2）**（0.5 天/连接器）— 验证事务原子性语义
  - `should_transaction_commit`：commit 后全部可见
  - `should_transaction_rollback`：rollback 后旁路断言目标端无数据
- ✅ **⑦ 索引 / 约束 / 外键（9）**（1 天/连接器）— 调用对应 Function 后旁路核对元数据定义
  - `should_create_index` / `should_query_indexes` / `should_delete_index`：索引创建/查询/删除
  - `should_create_constraint` / `should_query_constraints` / `should_drop_constraint`：约束创建/查询/删除
  - `should_create_foreign_key_constraint` / `should_query_foreign_key_constraints` / `should_drop_foreign_key_constraint`：外键创建/查询/删除（含辅助父表清理 `dropForeignKeyAuxTable`）
- ✅ **⑧ 字段级 DDL（4）**（0.5 天/连接器）— 字段 DDL 事件后旁路断言表结构与默认值填充
  - `should_new_field`：新增字段
  - `should_drop_field`：删除字段
  - `should_alter_field_name`：字段改名
  - `should_alter_field_attributes`：改字段属性
- ✅ **⑨ 分区表与 offset 管理（8）**（1 天/连接器）— 预置分区父/子表，断言分片结果；offset 函数配合 streamRead 断点场景
  - `should_create_partition_table` / `should_query_partition_tables` / `should_drop_partition_table`：分区表创建/查询/删除
  - `should_count_by_partition_filter`：按分区过滤计数
  - `should_get_read_partitions`：分区读取计划
  - `should_get_stream_offset` / `should_flush_offset`：offset 获取与刷新
  - `should_query_field_min_max`：字段极值查询（分片切分依据）
- ✅ **⑩ TapValue 编解码契约（10）**（框架内置，接入仅需方言适配）— 通过 EngineCodecs 做引擎侧 codec 全链路往返，逐类型断言不丢值
  - `should_wrap_generated_values_to_tap_value` / `should_unwrap_tap_value_to_plain_values`：包装/解包
  - `should_wrap_unwrap_round_trip_keep_values`：往返不丢值
  - `should_preserve_origin_value_when_unwrapping`：解包保留原始值
  - `should_write_records_via_engine_codec_roundtrip`：引擎 codec 往返写入
  - `should_wrap_read_back_values_to_tap_value`：回读值再包装
  - `should_wrap_null_and_boundary_values`：NULL / 边界值
  - `should_wrap_special_value_samples`：特殊值样本
  - `should_wrap_unwrap_nested_types`：嵌套类型
  - `should_validate_wrap_types_against_spec_through_database`：对照 spec 经数据库验证类型
- ✅ **⑪ 命令执行与原始查询（6）**（框架内置，按需方言适配）
  - `should_execute_command` / `should_execute_command_v2`：命令执行 v1/v2
  - `should_run_raw_command` / `should_count_raw_command`：原始命令执行/计数
  - `should_export_event_sql`：事件导出 SQL
  - `should_get_current_timestamp`：源端当前时间戳
- ✅ **⑫ 控制信号、回调与框架校验（8）**（框架内置）
  - `should_after_initial_sync`：初始同步后回调
  - `should_control` / `should_process_control`：控制信号下发/处理
  - `should_command_callback`：命令回调
  - `should_error_handle`：错误处理分类
  - `should_connector_website` / `should_table_website`：连接器/表文档元信息
  - `should_all_capabilities_implemented_and_covered`：**框架级校验**——强制 `requiredCapabilities()` 声明与实现/用例覆盖的完备性

### 3.2 引擎（iengine）集成测试（`tapdata/iengine/iengine-app/src/it`，🔄 部分覆盖）

> **落地位置修订**：实际落地在 `iengine-app/src/it`（`EngineIT` / `MySqlMongoIT` / `EngineRuntime` / `MockTM` 等），**并非**原计划的"新建 `tapdata-it/engine-it` 模块"。输入 `TaskDto` + 真实源/目标库，经 `HazelcastTaskService` 建 DAG → Jet 执行，旁路断言目标端数据、任务状态、offset。按 engine-it.md 的 D1-D12 维度分组：

- ✅ **引擎启动与心跳（基建，关联 L2-01 / L2-11）**
  - ✅ `should_engine_start_and_heartbeat`：调度器就绪、单例锁占用、心跳上报 MockTM
  - ✅ `should_task_full_flow_smoke`：任务全流转冒烟——下发到全量写完，目标数据与源一致
- 🔄 **D1 任务生命周期（对应 L1E-01 / L1E-08 / L1E-10）**
  - ✅ `should_start_task_from_wait_run`（L1E-01）：wait_run 认领为 running，全量写完进入增量
  - ✅ `should_idempotent_start`（L1E-01）：重复启动信号不重建 DAG、不重读全量
  - ✅ `should_graceful_stop`（L1E-08）：下发停止信号，任务落 stopped，资源释放
  - ✅ `should_natural_complete`（L1E-08）：全量任务跑完落 complete，端到端一致
  - ✅ `should_error_then_retry`（L1E-10）：模型加载返回空，任务落 runError
- 🔄 **D2 全量同步（对应 L1E-02）**
  - ✅ `should_normal_snapshot_serial`（L1E-02）：多表全量逐表串行，每表只读一次不重读
  - ✅ `should_snapshot_complete_event`（L1E-02）：全部表读完，任务切换增量阶段
- ✅ **D3 增量同步与事件类型（对应 L1E-03 / L1E-04）**
  - ✅ `should_incremental_insert`（L1E-03）：源端新插行流转到目标端
  - ✅ `should_incremental_update`（L1E-03）：源端行更新同步到目标端
  - ✅ `should_incremental_delete`（L1E-03）：源端删除行在目标端消失
  - ✅ `should_offset_advance_after_write`（L1E-04）：增量写入到达目标端后 offset 推进
- 🔄 **D4 目标端写入与一致性（对应 L1E-02 / L1E-05）**
  - ✅ `should_data_consistent_end_to_end`（L1E-02/05）：全量+增量双路径写入，逐行逐列一致
  - ⬜ 写入策略分支（L1E-05 缺口）：唯一键冲突下 insert_on_exists / update / ignore 分策略断言
- ✅ **断点续跑（对应 L1E-04）**
  - ✅ `should_restart_replay_no_loss`（L1E-04）：停止后重启，从 offset 续跑不丢不重
- ⬜ **待建用例（引擎侧缺口）**
  - ⬜ L1E-06 自动建表与类型映射：不预建目标表启动任务，旁路断言目标表结构与类型
  - ⬜ L1E-07 DDL 同步：源端 add/drop field 等 DDL 按三层闸过滤传播落库

## 六、落地排期与时间预测（人+AI 模式）

### 6.0 人+AI 工作量模型

AI 协同方式沿用 tapdata-it.md 阶段 1 思路：**知识库契约条目（tapdata-wiki）+ 测试模板 + 模块源码作为 AI Context，AI 生成用例初稿，开发者/SDET 人工校准后入库**。压缩系数按工作性质分档（人工校准与真实环境调试无法被替代）：

| 工作类型 | 典型内容 | 压缩系数 | 依据 |
|---|---|---|---|
| 模板化用例生成 | ConnectorIT 接入配置、契约测试、MockMvc 用例、API 用例、数据构造与断言代码 | 50%~60% | 有接入示例/Controller 源码/wiki 契约条目可直接作 Context，AI 初稿可用率高 |
| 联调与框架建设 | engine-it 模块骨架、真实数据库容器联调、跨模块（TM↔引擎）环境搭建 | 30%~40% | AI 生成骨架，真实执行路径问题需人工定位 |
| Flaky 治理与稳定性分析 | CDC 时序伪失败归因、长跑监控、HA 注障演练、集群操作 | 10%~30% | 依赖真实环境观察与经验判断，AI 仅辅助日志分析 |

> 注：压缩系数已包含 AI 生成初稿的时间（分钟级）与人工校准时间；校准成本随知识库校正质量下降（阶段 1 知识库人工校正越准，AI 初稿可用率越高，这也是先建知识库的原因）。

### 6.1 排期表（人+AI 口径）

**人力假设**：2 名连接器/引擎 Dev + 1 名 SDET，每人按 AI 辅助后产能计；执行环境复用自托管 runner（已就绪）+ K8s 集群（product-it-core 动态部署）。累计约 **84 人天**（纯人工口径约 144 人天，压缩 ~42%）。

| 阶段 | 周期 | 内容（对应上文用例） | 工作量（人+AI） | 里程碑出口 |
|---|---|---|---|---|
| P1：L0 收口 + Connector IT 首批 | 第 1 周 | L0 契约测试模板化补齐（~3）；MySQL/MongoDB/PostgreSQL 接入 ConnectorIT（~3，MySQL/Mongo ✅ 已接入） | ~6 人天 | 首批 3 连接器 IT 随 PR 门禁运行 |
| P2：L1 Connector 扩面 + 引擎 IT 启动 | 第 2 周 | Oracle/Kafka 接入（~2）；引擎 IT D1-D4（~6，✅ 已落地） | ~8 人天 | 5 连接器全接入；引擎 IT 首批用例 |
| P3：L1 收口（引擎/TM/API Server） | 第 3-5 周 | L1E-05~10 缺口（~10）；TM harness 基建 ✅ 已就绪 + 首样板 ✅，L1T-01~10 在 `manager/tm/src/it` 扩面（~11）；L1A-01~05（~5） | ~26 人天 | **L1 全量完成**（累计 ~37 人天） |
| P4：L2 产品能力 | 第 5-7 周（与 P3 尾部并行） | L2-01~12（WebSocket/调度/热加载/模型/告警/指标等；L2-01/02 已由 `EngineOnlineRescheduleIT` 首样板覆盖，L2-03/11 已部分覆盖） | ~22 人天 | **L2 全量完成**，纳入 Daily 回归 |
| P5：L3 新框架用例扩面 + CI 门禁 | 第 7-10 周 | product-e2e L3-F 冒烟/黄金路径扩面（F1/F2/F12 优先，~12）；product-stability HA/长跑/故障注入用例（S1/S3 优先，~8）；RC 门禁 + 定时任务接入 + 报告汇总（~2） | ~22 人天 | **L3-F 纳入 RC 门禁 + L3-S 定时专项上线** |
| 缓冲 | 第 11 周 | Flaky 治理、覆盖率门禁（≥80%）固化、文档回填知识库 | ~3 人天 | 三层门禁常态化 |

**总体预测：约 11 周（~2.5 个月），累计约 84 人天**（纯人工口径约 144 人天 / 15 周；同等人力下日历周期缩短 ~27%）。关键节点：
- 第 1 周末：L1 Connector 首批上线（最快可感知收益）；
- 第 5 周末：L1 全量（单 Module 集成测试体系成型）；
- 第 7 周末：L2 全量（产品能力回归自动化）；
- 第 10 周末：L3-F 纳入 RC 门禁 + L3-S 定时专项上线；
- 第 11 周末：三层 CI 门禁常态化。

**排期风险与对策**：① CDC 类 L1C-⑤/L1E-03/04 工作量波动大——按"容器预置 CDC 配置模板"先行固化（P1 内完成），复杂连接器允许进入 P3 缓冲；② L2-03 热加载涉及 PDK 运行时行为，若发现框架缺口，单独开分支评估（可能触发 PDK 层改造，届时范围上报）；③ 企业版连接器需 `tapdata` 与 `tapdata-enterprise` 平级目录 + `-P enterprise` 构建，环境准备前置到 P1（已由 DB2iConnectorIT 验证）；④ L3-S HA/长跑依赖 K8s 多副本环境与故障注入能力，若 product-it-core 的 `DistributedHaDeployment` 在真实集群上发现缺口，允许将部分 L3-S 用例顺延至缓冲周。
